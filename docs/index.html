01 / Project brief

One operational record,
not a collection of forms.

The system follows the incident across intake, classification, assignment, investigation, containment, recovery, and review—while enforcing who can see and change each part.

DOMAIN MODEL / 01

The incident is the center of the system.

Taxonomy, analyst assignments, investigation notes, IOCs, private evidence metadata, response actions, status transitions, and audit records stay connected to one case.

02 / Controlled lifecycle

Seven states.
Explicit transitions.

The workflow is encoded in a dedicated service with allowed forward paths, transition notes, history records, and a separate permission for closure.

  1. 01ReportedStructured intake
  2. 02TriagedScope and severity
  3. 03AssignedClear ownership
  4. 04InvestigatingNotes, IOCs, evidence
  5. 05ContainedThreat isolated
  6. 06ResolvedRecovery complete
  7. 07ClosedPermission-gated

Rule exampleInvestigating→Contained or Resolved

AccountabilityEvery accepted change creates transition history and an audit event.

03 / Product interface

Operational density,
kept readable.

The application uses a focused dark interface for long-running security work, with role-aware navigation and dashboards calculated from real incident records.

UI PRINCIPLE

Calm surfaces, strong hierarchy, and restrained status color let operational information carry the visual weight.

04 / Engineering evidence

Built past the demo.
Designed to be maintained.

The portfolio surface is visual; the repository demonstrates the architecture, authorization boundaries, data model, and regression coverage behind it.

02

Defense in depth

Middleware, Gates, permissions, scoped queries, and interface visibility reinforce the same access rules.

03

Relational domain model

04
